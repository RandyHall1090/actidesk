# spec/plan.md — ActiDesk (formerly "Online Shock-and-Awe Portal", renamed 2026-09-17)

> Implementation plan. This is the build map, not the product spec (that's PRD.md).

## 1. Overview
A **multi-tenant** Next.js + Supabase app with two surfaces: an authenticated rep/admin dashboard (asset library, package creation, tracking, team management) scoped to the signed-in user's organization, and a public renderer that serves the personalized desk-flat-lay page — branded with the sending org's logo — at a unique URL per prospect. Modeled on TMT's Shockbox tool, but Securafy owns the platform and is its first tenant, not its only one.

## 2. Architecture
- **Frontend/Backend**: Next.js (App Router) — one app, route groups for `(dashboard)` [authenticated] and `s/[slug]` [public]
- **Auth & DB**: Supabase (Auth + Postgres + Storage) — email+password (not magic links; see Tech decisions)
- **Multi-tenancy**: a real `orgs` table; every tenant-scoped table (`profiles`, `assets`, `packages`) carries an `org_id` FK; RLS policies gate every read/write by the caller's own `org_id`. Signup matches a new user to a tenant by email domain (see below) — there is no shared login across tenants and no cross-tenant visibility, verified live (see Testing).
- **Video/audio hosting**: Vimeo (unlisted) — app stores the Vimeo video/audio ID and embeds via player
- **Document/image storage**: Supabase Storage (brochures, business card images, magazine cover, company logos)
- **CRM sync**: HubSpot API — Securafy-specific (its own portal); upsert contact + log a timeline event on package creation. Not available to other tenants in v1 (see PRD non-goals).
- Data flow: rep action in dashboard → writes `packages` + `package_assets` rows (scoped to their `org_id`) → generates slug → public route reads that data server-side via `SECURITY DEFINER` lookup functions (never a direct table read — see T5/T9) → prospect interactions write `tracking_events` rows → dashboard reads them back for the "My Sites" view

## 3. Tech decisions
- **Next.js + Supabase** — matches workspace default stack, fastest path to auth + Postgres + storage without standing up separate services
- **Email + password, not magic links** — Securafy's own email security (Safe-Links-style scanning) was consuming the one-time login link before a real click ever happened, confirmed in the Supabase auth logs (repeated `HEAD` requests from Microsoft mail-scanner IPs). Password auth sidesteps the whole class of problem. See T1b.
- **Multi-tenant via email-domain matching, not invite codes** — simplest self-service mechanism: a new domain creates an org (creator becomes admin), a matching domain joins it (as rep). One domain per org for v1; a company with multiple domains is a known limitation, not solved until it's a real request.
- **One fixed template for v1** — avoided building a template/layout engine before proving the core workflow; hardcoded slot positions for the single desk-scene layout. Superseded by T10: layouts are now a small code-defined registry (`src/lib/packages/layouts.ts`), not a DB table — adding one is still always a code+deploy task (real desk art can't be self-service), so this stays deliberately lightweight rather than becoming a general layout engine.
- **Vimeo for video/audio** — avoids self-hosting large media, re-encoding, and bandwidth costs; Vimeo tooling is already available
- **Shared platform domain, path-based URLs** (`/s/[slug]`) — no per-tenant subdomain for v1 (this superseded an earlier "subdomain of securafy.com" decision made before multi-tenancy was in scope — a subdomain of Securafy's own domain makes no sense once other companies are tenants). Package links already resolve by slug alone, independent of tenant, so this generalizes cleanly; per-tenant custom domains (matching TMT's own model) are a future feature, not v1.
- **Rep sends the link themselves, app doesn't email prospects** — avoids transactional email deliverability/domain setup for v1
- **HubSpot sync on create, Securafy-only** — keeps the CRM as source of truth for Securafy's own prospect activity; a general per-tenant CRM integration is future work, not v1
- **Company logo is publicly readable** — it's branding, not secret; any tenant's uploaded logo is servable to anon so it can render on that tenant's public package pages
- **HubSpot Contact-record launcher uses a developer-platform "app card" UI extension, not a no-code link** — HubSpot's no-code Record customization cards can't build a per-contact dynamic outbound URL (confirmed against HubSpot's own current docs before building anything); HubSpot's own docs point at app cards (UI extensions) as the supported way to do this. Private distribution + static auth — no OAuth, no marketplace listing, single-portal only (46124718), same Securafy-only reasoning as the existing HubSpot sync. See T29.
- **In-dashboard help chat is grounded in one curated content file, not repo/code access** — a rep-facing AI widget wired to this actual GitHub repo would expose proprietary source and cut against every other access-control decision in this app (RLS, security-definer lookups, signed URLs). Instead it answers only from an editable help-content doc, via Vercel AI Gateway (Claude), streamed from a session-checked route handler. Dashboard-only — not mounted on the public `/s/[slug]` route. See T30.
- **Dark mode is a real per-page retrofit, not a CSS variable flip** — this app was built deliberately fixed-light (`color-scheme: light` in `globals.css`, to fix a real light-on-dark native-input bug during login), so a working toggle means adding actual `dark:` variants across every dashboard page, not just the shared header. Dashboard only; the public `/s/[slug]` page keeps its own forced styling (see T25) untouched. See T31.
- **Meeting-scheduling CTA is a plain rep-entered URL, not a Calendly integration** — this app is multi-tenant, and a rep's scheduling link could be Calendly, Cal.com, HubSpot Meetings, or anything else; auto-fetching from one specific connected Calendly account wouldn't generalize past that one account. Each rep sets their own link once on `/account`; the public page shows the *creating rep's* link (matches every other slot's already-personalized-per-rep model), not one shared org-wide link. See T32.
- **Gate Desk API integration is a real service-account row, not a shared-secret-only bypass** — Actiforge's separate "Gate Desk" campaign backend creates packages server-to-server via a new `POST /api/packages` route, bearer-token authenticated against a new `GATE_DESK_API_KEY`. Every API-created package's `created_by` points at a real `profiles`/`auth.users` row (`gate-desk-service@securafy.com`, created directly via SQL with `encrypted_password` left `NULL` — it can never actually log in, it only exists as an FK target `packages_insert_own`'s RLS can check against, same as any other row's owner). The route uses the service-role client (`createAdminClient()`, same as T12's admin mutations) since a bearer-token caller has no real Supabase session for RLS to evaluate. Explicitly and permanently excludes `syncPackageToHubSpot()` — API-created packages must never generate a HubSpot contact, only dashboard-created ones do. See T33.
- **Renamed to ActiDesk (from "Online Shock-and-Awe Portal"), 2026-09-17** — going to market under a name TMT already uses ("Shock and Awe"/"Online Shock and Awe") for a directly comparable product in the exact same MSP/MSSP sales-tool niche was a reputational-confusion risk even though the formal trademark risk came back low (no relevant-class USPTO mark found — see `plans/reports/2026-09-17-billing-research/naming-trademark.md`). ActiDesk fits the existing Acti-/Forge brand family (ActiScan, ActiScore, Actishield, Actiforge) and still names the actual desk-scene mechanic. Only current/forward-facing docs and user-visible text were updated (CLAUDE.md, PRD.md, this file's title, `package.json`, page titles/copy, the help-chat content, the HubSpot note body). Historical plan/report files that predate the rename intentionally keep their original "Shock and Awe" wording — they're a record of what was true when written, not live product docs. **Not yet renamed** (deliberately, pending explicit go-ahead since each is a live/deploy-affecting identifier): the GitHub repo, the Vercel project, the Supabase project name, the deployed domain, and the Securafy-internal HubSpot card extension (`hubspot-extension/`, which has its own real HubSpot app registration).
- **Billing is self-serve Stripe, per-seat, sales-motion-free** — this app is meant to be resold to other tenants (not just Securafy's own use), so billing had to move from "free, unrestricted signup" to a real subscription gate. Chose self-serve Stripe Checkout (not a manually-invoiced sales-assisted model) since the product is meant to onboard strangers off the internet, not only clients Securafy sells to directly. Per-seat pricing (quantity = active rep count), not flat-per-org or usage-based, matches how this class of sales-enablement tool is typically priced and scales fairly between a 2-person shop and a large team. New orgs get a 14-day free trial (no card required) before a paywall, and a lapsed/expired org is **soft-blocked** (existing content, including already-sent `/s/[slug]` prospect pages, stays fully viewable; only *creating new* content is blocked) rather than locked out entirely — friendlier to win back a lapsed customer. Ongoing self-service billing management (card updates, cancellation, invoices) goes through the Stripe-hosted Customer Portal, not a custom UI. General promo codes (e.g. a launch discount) use Stripe's native `allow_promotion_codes` on Checkout — zero app code, codes are created directly in the Stripe Dashboard. A handful of early beta-tester accounts get a special graduated discount (free for 12 months, then 50% off for life) via a manually-configured Stripe Subscription Schedule per person, not generalized in-app automation — not worth building for a one-time small cohort. Provisioned via the Vercel Marketplace Stripe integration, not a hand-wired SDK. Securafy's own org is permanently billing-exempt (it's the platform operator, not a customer). See T34.

**RLS recursion bug (found and fixed)**: `profiles`' own SELECT policy queried `profiles` again to check admin status, which Postgres re-applies RLS to — recursing infinitely the moment any real query touched it (a rep's own dashboard included). Static analysis (the Supabase security advisor) never caught this; it only surfaced by actually running queries as each role against the live database. **PUBLIC-grant gotcha (recurred twice)**: Postgres grants `EXECUTE` to the `PUBLIC` pseudo-role by default when a function is created, AND a function can separately end up with a *direct* grant to a specific role (`anon`) that is NOT the same thing and is unaffected by `revoke ... from public`. `prevent_self_role_escalation()` had exactly this — a direct `anon` grant that survived two `revoke ... from public` attempts, only found by reading the raw ACL (`pg_proc.proacl`) instead of trusting the advisor or assuming a revoke "worked" (migrations 0009/0011). **Lesson: always revoke `from public, anon, authenticated` explicitly** for any function that should never be callable directly (0002 got this right from the start); and verify with `has_function_privilege(...)` or the raw ACL, not just by re-running the advisor once.

The extension's runtime has no real `window`/`document` (confirmed via HubSpot's own TypeScript/ESLint guidance, which treats both as build-time errors) — `Link` is the documented, sanctioned way to leave the HubSpot UI, not a raw `window.open`. **No changes needed in the Next.js app itself** — the `prospect_name`/`prospect_email` URL-prefill on `/packages/new` already shipped (see the "New Package defaults..." commit, `5ebffad`), and its own code comment already anticipated "an external link (e.g. a HubSpot contact-record link)".
