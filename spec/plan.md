# spec/plan.md — Online Shock-and-Awe Portal

> Implementation plan. This is the build map, not the product spec (that's PRD.md).

## 1. Overview
A **multi-tenant** Next.js + Supabase app with two surfaces: an authenticated rep/admin dashboard (asset library, package creation, tracking, team management) scoped to the signed-in user's organization, and a public renderer that serves the personalized desk-flat-lay page — branded with the sending org's logo — at a unique URL per prospect. Modeled on TMT's Shockbox tool, but Securafy owns the platform and is its first tenant, not its only one.

## 2. Architecture
- **Frontend/Backend**: Next.js (App Router) — one app, route groups for `(dashboard)` [authenticated] and `s/[slug]` [public]
- **Auth & DB**: Supabase (Auth + Postgres + Storage) — email+password (not magic links; see Tech decisions)
- **Multi-tenancy**: a real `orgs` table; every tenant-scoped table (`profiles`, `assets`, `packages`) carries an `org_id` FK; RLS policies gate every read/write by the caller's own `org_id`. Signup matches a new user to a tenant by email domain (see below) — there is no shared login across tenants and no cross-tenant visibility, verified live (see Testing).
- **Video/audio hosting**: Vimeo (unlisted) — app stores the Vimeo video/audio ID and embeds via player
- **Document/image storage**: Supabase Storage (brochures, business card images, magazine cover, company logos)
- **CRM sync**: HubSpot API — Securafy-specific (its own portal); upsert contact + log a timeline event on package creation. Not available to other tenants in v1 (see PRD non-goals).
- Data flow: rep action in dashboard → writes `packages` + `package_assets` rows (scoped to their `org_id`) → generates slug → public route reads that data server-side via `SECURITY DEFINER` lookup functions (never a direct table read — see T5/T9) → prospect interactions write `tracking_events` rows → dashboard reads them back for the "My Sites" view

## 3. Tech decisions
- **Next.js + Supabase** — matches workspace default stack, fastest path to auth + Postgres + storage without standing up separate services
- **Email + password, not magic links** — Securafy's own email security (Safe-Links-style scanning) was consuming the one-time login link before a real click ever happened, confirmed in the Supabase auth logs (repeated `HEAD` requests from Microsoft mail-scanner IPs). Password auth sidesteps the whole class of problem. See T1b.
- **Multi-tenant via email-domain matching, not invite codes** — simplest self-service mechanism: a new domain creates an org (creator becomes admin), a matching domain joins it (as rep). One domain per org for v1; a company with multiple domains is a known limitation, not solved until it's a real request.
- **One fixed template for v1** — avoided building a template/layout engine before proving the core workflow; hardcoded slot positions for the single desk-scene layout. Superseded by T10: layouts are now a small code-defined registry (`src/lib/packages/layouts.ts`), not a DB table — adding one is still always a code+deploy task (real desk art can't be self-service), so this stays deliberately lightweight rather than becoming a general layout engine.
- **Vimeo for video/audio** — avoids self-hosting large media, re-encoding, and bandwidth costs; Vimeo tooling is already available
- **Shared platform domain, path-based URLs** (`/s/[slug]`) — no per-tenant subdomain for v1 (this superseded an earlier "subdomain of securafy.com" decision made before multi-tenancy was in scope — a subdomain of Securafy's own domain makes no sense once other companies are tenants). Package links already resolve by slug alone, independent of tenant, so this generalizes cleanly; per-tenant custom domains (matching TMT's own model) are a future feature, not v1.
- **Rep sends the link themselves, app doesn't email prospects** — avoids transactional email deliverability/domain setup for v1
- **HubSpot sync on create, Securafy-only** — keeps the CRM as source of truth for Securafy's own prospect activity; a general per-tenant CRM integration is future work, not v1
- **Company logo is publicly readable** — it's branding, not secret; any tenant's uploaded logo is servable to anon so it can render on that tenant's public package pages

**RLS recursion bug (found and fixed)**: `profiles`' own SELECT policy queried `profiles` again to check admin status, which Postgres re-applies RLS to — recursing infinitely the moment any real query touched it (a rep's own dashboard included). Static analysis (the Supabase security advisor) never caught this; it only surfaced by actually running queries as each role against the live database. Fixed with a `SECURITY DEFINER` `is_org_admin()` helper (migrations 0005–0007) that breaks the cycle.

**PUBLIC-grant gotcha (recurred twice)**: Postgres grants `EXECUTE` to the `PUBLIC` pseudo-role by default when a function is created, AND a function can separately end up with a *direct* grant to a specific role (`anon`) that is NOT the same thing and is unaffected by `revoke ... from public`. `prevent_self_role_escalation()` had exactly this — a direct `anon` grant that survived two `revoke ... from public` attempts, only found by reading the raw ACL (`pg_proc.proacl`) instead of trusting the advisor or assuming a revoke "worked" (migrations 0009/0011). **Lesson: always revoke `from public, anon, authenticated` explicitly** for any function that should never be callable directly (0002 got this right from the start); and verify with `has_function_privilege(...)` or the raw ACL, not just by re-running the advisor once.

**Asset upload 4.5MB wall — resolved (2026-09-09)**: Randy reported large PDF uploads crashing with a hard client-side error. Root-caused through several wrong turns before landing on the real answer:
1. First assumed it was Next.js's Server Actions `bodySizeLimit` (default 1MB) — raised it, files near the new cap still failed the same way.
2. Raised it further and suspected `proxy.ts` (auth middleware) buffering the body — Next.js's `proxyClientMaxBodySize` defaults to 10MB, separately from `bodySizeLimit`. Raised that too and excluded `/library` from the middleware matcher entirely. Still failed identically.
3. Only network-level inspection of the actual browser request (not app logs — those never even showed the request landing) revealed the real, unambiguous signal: HTTP **413**. Fetching current Vercel docs (`/docs/functions/limitations`, dated 2026-08-24) confirmed: Vercel Functions have a **hard 4.5MB request body cap** (`FUNCTION_PAYLOAD_TOO_LARGE`) enforced at the platform level — not configurable via `next.config.ts` at all, contradicting an assumption carried into this conversation that Vercel supports 100MB bodies (that must refer to something else, e.g. a different runtime/beta feature; the current docs are unambiguous that the *default* Functions limit is still 4.5MB).

All three of the above workaround attempts were reverted (`next.config.ts` back to empty, `proxy.ts` matcher back to original) since none of them were the real fix and leaving them in would misrepresent what's actually happening.

**Real fix** (Vercel's own recommended pattern for large uploads, adapted to Supabase Storage instead of Vercel Blob): the file now uploads directly from the browser to Supabase Storage (`LibraryClient.tsx`), never passing through a Vercel Function at all. The existing Storage RLS policies already permitted this with no migration needed — they check `auth.uid()`, which resolves identically whether the request comes from the server (cookie-based session) or the browser (client-side session), since it's the same authenticated end user either way. The Server Action (renamed `uploadFileAsset` → `createFileAssetRecord`) now only receives the resulting storage path and file size to create the DB row — a request body of a few bytes regardless of file size. Verified live against production with real ~19.9MB and ~40MB files that were failing before.

**Sparse public package pages rendered tiny — resolved (2026-09-09)**: Randy reported a "Vimeo error," but the video embedded fine (confirmed via accessibility snapshot — full player UI, correct title/owner). The real bug: a package with few slots filled (e.g. video only, no letter or brochures) rendered the *entire* public page at ~87px wide instead of 768px, everything shrunk together. `PackageView.tsx`'s outer container relied on implicit flex-stretch (body is a column flex container, `layout.tsx`) for its width instead of declaring one explicitly — confirmed via live DOM inspection that width tracked content amount (87px with nothing else on the page, 395px once a letter was added, still short of 768px) rather than stretching to fill the flex cross-axis. Fixed with an explicit `w-full`, matching the pattern every other root page container in the app already uses (`flex-1` on dashboard/login/signup roots) instead of relying on bare stretch.

**GoTrue seed-user gotchas (recurring across sessions)**: creating a test `auth.users` row directly via SQL (needed since there's no service-role key available to use the Admin API) requires, beyond the obvious columns: a matching `auth.identities` row, several nullable token columns explicitly set to `''` (not `NULL` — GoTrue's Go driver can't scan a NULL into those), and `instance_id = '00000000-0000-0000-0000-000000000000'` (defaults to `NULL` if omitted, which makes GoTrue's user lookup silently fail with "Invalid login credentials" rather than a clearer error). All confirmed by hitting each one for real, not assumed.

**HubSpot env var naming (deliberately not `HUBSPOT_PRIVATE_APP_TOKEN`)**: the token is read from `SECURAFY_HUBSPOT_TOKEN`, not the more obvious generic name. Found live: Randy's machine already has a Windows User-level environment variable named `HUBSPOT_PRIVATE_APP_TOKEN` (a different, unrelated token, kept intentionally for another project) — Next.js's env loader never overrides a key already present in `process.env`, so the real token in `.env.local` was being silently ignored no matter what was written there, with no error until the API call itself failed. Renamed to a Securafy-specific var everywhere (`.env.example`, `.env.local`, `src/lib/hubspot.ts`, Vercel prod+preview) to sidestep the collision rather than touch Randy's global machine state. **Lesson: prefer app-specific env var names over generic ones for anything that isn't a widely-standardized convention** — a generic name is one collision away from being silently shadowed with no error.

**Library scope dropdown resetting after every upload — resolved (2026-09-09)**: Randy reported that adding a document to the Company Library flipped the dropdown back to "My library" for the very next upload, forcing it to be re-selected every time. Root cause: React 19's `useActionState` calls a native `form.reset()` after every successful action, which overwrites even a `value`-controlled `<select>`'s DOM value directly — lifting the scope into parent state with a controlled `value` prop alone was not enough (confirmed live, it still snapped back). Fixed by adding a `ref` + `useEffect` that re-asserts the real value on the `<select>` DOM node right after React's reset fires. Verified live with two consecutive company-scope uploads, both correctly holding the selection.

**Stale upload error persisting across library tab switches — resolved (2026-09-09)**: Randy reported "error uploading [vimeo url]" on the Video tab; the Vimeo link itself was fine (added successfully with no error) — the real bug was a leftover "Name and a file are both required" error message (which belongs to a file-based tab like Documents) still showing on the Video tab, a link-based tab with no file field at all. Root cause: `key={kind}` was on the inner `<form>` inside `UploadForm`, which only remounts that DOM subtree — not `useActionState`'s hook state, which lives in the `UploadForm` component itself and doesn't remount just because a key deeper in its own JSX changes. Fixed by moving the key to `<UploadForm key={activeKind}>` at its call site in `LibraryClient`, forcing a full remount (hook included) on every tab change. Verified live: triggered the error on Documents, switched to Video, confirmed it no longer appears.

**T10 Templates — desk-scene layouts + content presets (2026-09-09)**: Randy asked for the ability to "create Templates," reversing a documented v1 non-goal. Scoped with him first via clarifying questions: (1) "Templates" means both selectable desk-scene layouts AND reusable content presets (asset picks + letter text); (2) admins only manage both; (3) start with 2 layouts total, shipped as a real mechanism with a clearly-labeled placeholder second layout rather than blocking the build on a full live art-generation session (that's a separate, decoupled follow-up).

- **Layouts are a code registry, not a DB table** (`src/lib/packages/layouts.ts`) — every layout is inseparable from a committed image + hand-tuned positions, so a DB table would add indirection without adding real self-service capability (adding one is always a code+deploy step regardless of who's "admin"). `packages.template_id` already existed in the schema from day one but was completely dead code (fetched by the public RPC, never used) — this feature is largely wiring that up for the first time.
- **Tailwind v4 arbitrary-value classes can't be built from runtime data** — the original `DeskScene.tsx` used literal classes like `left-[29%]` for every slot position; Tailwind statically scans source for literal class strings, so a class built as a template literal (`` `left-[${x}]` ``) wouldn't exist in the compiled CSS and would silently render unpositioned. Fixed by moving only the per-layout values (left/top/width/rotate) to inline `style`, keeping every other class (radius, shadow, ring, the `cqw`-based font sizes) as static literal classes exactly as before — this fully preserved the deliberate mobile `cqw`-scaling fix from T3.
